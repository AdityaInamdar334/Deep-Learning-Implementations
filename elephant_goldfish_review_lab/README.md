A **standalone educational companion**, not an official Google EGM plugin or a replacement for its native fresh-subagent workflow.

**No external dependencies. Python 3.10+. No model API keys.** It **never calls an LLM**, doesn't automatically spawn isolated contexts, and doesn't execute project code. You must paste the generated packets into genuinely fresh review sessions. A fresh chat may still inherit product, project or user instructions, so it is not a security sandbox.

## Why this lab exists

The key experiment is to write a design with full conversational context, then pass **only the design** to new readers. A self-contained specification should survive the loss of the original conversation. This lab helps you construct the test, capture responses, and avoid falsely treating missing or failed reviews as passes. A separate security persona is an educational addition to EGM's documented default review flow.

## Quick start

From the project root:

```bash
python -m review_lab lint examples/webhook_spec_v1.md
python -m review_lab prepare examples/webhook_spec_v1.md --out out/round1
```

Open each `out/round1/packets/*.md` file in a **different fresh session** with a model of your choice. Do not give the reviewer the original brainstorming transcript, preferred solution, or other reviewers' reports. Save the returned JSON as `out/round1/responses/<reviewer>.json`.

```bash
python -m review_lab gate examples/webhook_spec_v1.md --responses out/round1/responses --out out/round1/gate.json
```

**Expected behavior without responses:** `NO-GO: INCOMPLETE OR INVALID REVIEW`, exit code `2`. This is deliberate. Missing reviews must never be counted as clean passes.

Revise the design. Then regenerate packets and ask new reviewers to review the new version:

```bash
python -m review_lab prepare examples/webhook_spec_v2.md --out out/round2
```

A response for the old spec cannot be used with the new spec because each packet and result is tied to the exact SHA-256 digest of its design. If you edit even one character, previous results become stale. This is a stricter-than-normal educational check, not an official EGM feature guarantee.

## View the synthetic demonstration

Five **hand-authored, simulated** review responses are in `reviews/simulated_v1/`. They are **not generated by an LLM** and are not an empirical result. They exist to show the JSON schema and fail-closed gate:

```bash
python -m review_lab gate examples/webhook_spec_v1.md --responses reviews/simulated_v1
```

The exit status is `2` because the sample contains blocker/major findings. `reviews/simulated_verdict.json` contains the expected report.

## Findings format

Example response (replace digest with value from `out/round1/manifest.json`):

```json
{
  "reviewer": "security",
  "status": "completed",
  "spec_sha256": "<digest>",
  "findings": [{
    "id": "SEC-01",
    "severity": "blocker",
    "evidence": "Architecture: directly POST to user-provided URL; no destination restriction or authorization noted",
    "recommendation": "Specify SSRF-safe destination validation, URL revalidation, and account-scoped authorization"
  }]
}
```

Allowed severities: `blocker`, `major`, `minor`. The gate requires all five reviewers to submit valid `completed` responses for the current spec. If **any** Blocker or Major remains, the gate says NO-GO. If none remain, it says **ELIGIBLE FOR HUMAN REVIEW**, never automatically approved. The script cannot judge whether a reviewer's evidence is correct or whether risk was actually resolved. Human judgment and tests are still required.

## What's included

- `examples/webhook_spec_v1.md` intentionally incomplete webhook design, with retry/idempotency/security gaps
- `examples/webhook_spec_v2.md` improved teaching example, not a production-ready specification
- `review_lab/` Python generator, simple linter, and conservative gate
- `tests/` deterministic unit tests
- `SOURCES.md` primary links, limitations and fact-check notes

## Scope / threats to validity

- The demo does not quantify LLM reviewer quality or defect reduction.
- It cannot verify that model provider sessions are truly isolated.
- The linter checks headings/placeholders, not correctness or safety.
- Same-model reviewers may share biases even in fresh contexts.
- A model's confident assertion is not source-code evidence.
- Read-only review access to a repository is still broader context than the design alone; document what each reviewer received.
- This is an educational protocol inspired by EGM and not a redistribution or fork of Google's official code.
